# Olist E-Commerce Analysis & Advanced SQL (Homework 4)

Проєкт присвячений поглибленому вивченню **PostgreSQL**, проектування реляційних схем (DDL), роботі з розширеними DML-операціями, складними об'єднаннями (`JOIN`), агрегаціями та побудовою бізнес-аналітики на основі публічного датасету **Olist Brazilian E-Commerce**.

## 📂 Структура виконаних завдань

### Етап 1: Setup, Raw-дані та Typed-схема
1. **Імпорт сирих даних:** Дані з Kaggle завантажено в проміжні таблиці з суфіксом `_raw` (тип даних `TEXT`).
2. **Проектування реляційної схеми:** Створено фінальну `typed`-схему з урахуванням найкращих практик інжинірингу даних:
   * Первинні ключі (`PRIMARY KEY`) та зовнішні ключі (`FOREIGN KEY` з `REFERENCES`).
   * Обмеження цілісності (`CHECK`-обмеження для статусів замовлень, цін та вагових характеристик).
   * Індекси для оптимізації пошуку (`CREATE INDEX` для унікальних ідентифікаторів та зовнішніх ключів).
3. **Міграція даних:** Перенесення даних із `raw`-таблиць у фінальні за допомогою `INSERT ... SELECT` із явним приведенням типів (`TIMESTAMP`, `NUMERIC`, `INTEGER`).

---

### Етап 2: DML-запити з PostgreSQL-фічами
Реалізовано чотири розширені DML-операції з використанням специфічних можливостей PostgreSQL:
1. **`INSERT ... RETURNING`:** Автоматизоване створення попереджень (`seller_alerts`) для проблемних продавців із миттєвим виведенням логу.
2. **`INSERT ... ON CONFLICT DO UPDATE` (Upsert):** Розрахунок та ідемпотентне оновлення агрегованого рейтингу продавців (`seller_score`) на рівні замовлень, що захищає від дублювання рядків при повторних запусках.
3. **`UPDATE ... FROM`:** Масове оновлення булевого прапорця запізнення (`is_late`) в таблиці `olist_orders` на основі порівняння фактичних і планових дат доставки.
4. **`DELETE ... RETURNING`:** Контрольоване очищення застарілих попереджень (старших за 30 днів) із логуванням видалених ідентифікаторів.

---

### Етап 3: RFM-сегментація (`customer_segments`)
* Створено дедуплікований вимір покупців (`olist_customer_dim`) за унікальним ідентифікатором (`customer_unique_id`).
* Побудовано таблицю `customer_segments` із production-подібними обмеженнями (`IDENTITY PK`, `UNIQUE`, `CHECK`).
* Наповнено таблицю на основі **RFM-аналізу** (Recency, Frequency, Monetary) з використанням динамічної контрольної дати із самого датасету та механізму `ON CONFLICT`.

---

### Етап 4: Складні JOIN-запити та бізнес-інтерпретація
Виконано 5 комплексних запитів для розв'язання аналітичних бізнес-задач:
1. **`INNER JOIN` (3+ таблиць):** Аналіз продажів у розрізі товарних категорій та географії покупців.
2. **`LEFT JOIN` + `COALESCE`:** Побудова профільних ознак клієнтів із коректною обробкою відсутності відгуків.
3. **`FULL OUTER JOIN`:** Порівняння географічного покриття штатів клієнтів та продавців (`both`, `customers_only`, `sellers_only`).
4. **`SELF JOIN`:** Пошук пар продавців, які працюють в одному штаті, але в різних містах.
5. **Anti-join (`NOT EXISTS` / `LEFT JOIN ... IS NULL`):** Виявлення замовлень, які досі не мають жодних відгуків від покупців.

---

### Етап 5: Агрегації, GROUP BY та STRING_AGG
* Розрахунок загального доходу на категорію товару з фільтрацією через `HAVING`.
* Обчислення середнього чека (AOV) по штатах із пороговим фільтром (`HAVING COUNT(*) >= 100`).
* Використання агрегаційної функції `STRING_AGG` для формування списків придбаних категорій в один рядок для кожного покупця.

---

### Етап 6: Віконні функції, Set Operations та Reflection
* **Set Operations:** Використання множин для порівняння геолокацій.
* **Window Functions:** Застосування віконних функцій (`ROW_NUMBER()` / `RANK()`) для визначення найновіших замовлень кожного користувача.
* **Reflection:** Написано професійну рефлексію щодо архітектурних рішень, грануляції даних (order-level vs item-level у відгуках) та уникнення витоків даних (`data leakage`).
